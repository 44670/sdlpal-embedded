# Consultation Q1: Memory and Asset Strategy for SDLPAL on a Constrained Embedded Target

## Ask

Please review the memory/resource-loading strategy for this SDLPAL port and propose a practical architecture for running it on the target below.

The expert receiving this note can assume zero prior knowledge of this project. The goal is not a general C cleanup. The goal is a concrete memory placement, asset preprocessing, and runtime loading plan that can make the game run reliably on the hardware.

## Target Hardware and Storage Model

- Fast SRAM: 300KB total. This should be treated as the scarce low-latency memory.
- PSRAM: 8MB total. Much slower than SRAM, but usable for larger mutable working sets.
- NOR flash: 16MB total, read-only at runtime, random accessible. Assume this is suitable for memory-mapped or low-overhead random reads if the port supports that.
- TF card: effectively unlimited capacity, but slow. It can hold the original game files and/or generated cache files, but runtime random reads from TF should be minimized.

Pre-decompression and offline asset conversion are a hard requirement for the embedded runtime. The runtime should not contain YJ1/YJ2/LZ4/etc. decompression code. Every resource pack payload consumed by the target runtime should already be in its final runtime-native representation before the pack is built. Full pre-decompression into 16MB NOR is not feasible, so large decompressed assets must be split between NOR and TF-backed resource packs.

Additional implementation goals:

- No `malloc`, `calloc`, `realloc`, or `free` in the embedded engine/resource path.
- Runtime memory should be explicit fixed storage: `uint8_t` buffers for SRAM/PSRAM, `const uint8_t` or `const` typed views for read-only NOR/pack data.
- Buffer sizes should be static and auditable. Avoid hidden dynamic allocation, even through thin wrappers. Do not introduce a memory-pool abstraction just to route data between SRAM and PSRAM; prefer normal named `uint8_t` static-storage buffers and verify their sizes from the ELF.
- The native SDL build must remain usable as the verification harness, with fixed SRAM/PSRAM arrays simulating the target memory layout.
- Resource usage must be checked from build artifacts using tools such as `size`, `objdump -h`, `objdump -t`, `nm -S --size-sort`, and linker map files.

## Project Background

This repository is SDLPAL, an SDL-based reimplementation of the classic Chinese RPG "Legend of Sword and Fairy" / PAL.

The engine code is mostly C, with a C++ RIX music player. The desktop code uses SDL surfaces, SDL audio, filesystem `FILE *`, and `malloc`/`calloc` directly. The original proprietary game data is not in the repo. For this investigation, the data files are at:

```text
/mnt/hgfs/deb13/PAL
```

The current data set appears to be a DOS/YJ1 PAL data set, not the Win95/YJ2 data set. Many graphics archives are MKF containers whose chunks are compressed with YJ1. Some MKFs contain raw chunks.

Important engine/resource concepts:

- Screen/game resolution is 320x200, mostly 8-bit indexed color.
- `FBP.MKF`: full-screen background images, compressed, usually decompress to 64,000 bytes.
- `MAP.MKF`: compressed map tile metadata. Each loaded map becomes a fixed 64KB tile array.
- `GOP.MKF`: raw tile sprite data for each map.
- `MGO.MKF`: scene/NPC/player walking sprites, compressed.
- `ABC.MKF`: enemy battle sprites, compressed.
- `F.MKF`: player battle and summon sprites, compressed.
- `FIRE.MKF`: magic/effect sprites, compressed.
- `RGM.MKF`, `BALL.MKF`, `DATA.MKF`, `SSS.MKF`: faces/items/data/scripts.
- `RNG.MKF`: cutscene animation data.
- `VOC.MKF`, `MUS.MKF`, `MIDI.MKF`: sound/music data.

## Startup and Runtime Flow

The high-level initialization order in `main.c` is:

1. `PAL_InitGlobals()`
2. `VIDEO_Startup()`
3. `PAL_InitUI()`
4. `PAL_InitText()`
5. `PAL_InitFont()`
6. input/resources/audio/AVI init

Important source paths:

- `global.c`: opens game data files, detects DOS/Win95 version, allocates and loads global game data.
- `res.c`: current scene resource loader. Loads the current map, event object sprites, and player walking sprites.
- `map.c`: loads one map plus its tile bitmap blob.
- `palcommon.c`: MKF chunk reading and YJ decompression wrapper.
- `video.c`: creates screen buffers/surfaces/textures.
- `font.c` and `fontglyph*.h`: built-in font storage and glyph loading.
- `text.c`: loads all words/messages into converted wide-string arrays.
- `battle.c` and `fight.c`: battle scene/background/sprite/effect loading.
- `rngplay.c`: RNG cutscene playback.
- `audio.c`, `sound.c`, `rixplay.cpp`, `resampler.c`: audio output, sound effects, music, resampling.

Normal scene loading happens through `PAL_LoadResources()` in `res.c`:

- `kLoadGlobalData`: calls `PAL_InitGameData()`.
- `kLoadScene`: frees prior scene resources, loads current map, loads all event object sprites for the scene.
- `kLoadPlayerSprite`: frees/reloads walking sprites for party/followers.

Normal frame rendering calls `PAL_MakeScene()` in `scene.c`:

- Draws both map layers to `gpScreen`.
- Applies wave effect.
- Adds player/event sprites and cover tiles to a fixed sort list.
- Sorts and blits all sprites.

Battle startup in `battle.c`:

- Loads player battle sprites from `F.MKF`.
- Loads enemy battle sprites from `ABC.MKF`.
- Loads battle background from `FBP.MKF`.
- Creates battle background and scene-buffer surfaces.
- Loads battle effect sprite from `DATA.MKF #10`.

- `MAP.MKF`: 14.6MB
- `FBP.MKF`: 4.6MB
- `MGO.MKF`: 3.36MB
- `ABC.MKF`: 2.15MB

That does not include `GOP.MKF` raw tile sprites at 11.5MB. Therefore, "pre-decompress everything into NOR" is not feasible with 16MB NOR. The target direction is instead: pre-decode/convert everything into runtime-native resource packs, place hot read-only chunks in NOR, and place large sequential raw/native chunks in TF-backed packs.

## Actual Current Runtime Memory Pressure

The following sizes are from source reading plus host-layout `sizeof` probes. Exact struct sizes will vary with pointer size and target ABI, but the conclusions are stable.

### Major Always-Resident or Long-Lived Data

- `fontglyph.h` defines `static unsigned char unicode_font[65536][32]`: about 2,097,152 bytes of mutable initialized data.
- `fontglyph.h` also defines `font_width[65536]`: about 65,536 bytes.
- `PAL_InitFont()` allocates `font_offset_x` and `font_offset_y`, each sized from `sizeof(font_width)`: another about 131,072 bytes total.
- The actual `WORD.DAT` + `M.MSG` corpus uses 2,631 unique characters. At 32 bytes per 16x16 glyph this is about 84KB before width/offset metadata, so a generated subset is much more plausible than the current full Unicode table.
- `resampler.c` defines static float LUTs:
  - `sinc_lut[16385]`
  - `window_lut[16385]`
  - `cubic_lut[4096]`
  - Total about 147KB of mutable static float tables.
- `GLOBALVARS` host `sizeof`: about 21KB before heap-loaded data.
- `TEXTLIB` host `sizeof`: about 376 bytes before text arrays.
- `BATTLE` host `sizeof`: about 4KB before battle sprite/surface allocations.

The font data alone cannot live in 300KB SRAM. It must be redesigned, placed outside fast SRAM, made const/read-only, subsetted, or loaded on demand.

The current embedded font slice proves the intended replacement shape for the real data: a host-built 88,432-byte FONT chunk in NOR, with 2,600 unique `WOR16` CJK glyphs and no mutable `unicode_font` table. It is not yet wired into the full desktop engine path.

### Global Game Data Heap

`PAL_InitGlobalGameData()` in `global.c` allocates these whole chunks:

- `SSS.MKF #0` event objects: 171,808 bytes.
- `SSS.MKF #4` scripts: 339,952 bytes.
- `DATA.MKF #0` stores: 378 bytes.
- `DATA.MKF #1` enemies: 11,200 bytes.
- `DATA.MKF #2` enemy teams: 3,900 bytes.
- `DATA.MKF #4` magic: 3,648 bytes.
- `DATA.MKF #5` battlefields: 780 bytes.
- `DATA.MKF #6` level-up magic: 400 bytes.

Total actual heap for these allocated chunks: 532,066 bytes.

The current embedded global-data slice does not mirror that heap layout. It copies only mutable default state into the existing `pal_psram_save_state` static array and maps read-only SSS/DATA tables directly from the generated NOR pack. For the audited data set this puts 182,176 bytes in PSRAM for event objects, scenes, DOS objects, and player roles, while keeping scripts and base tables read-only.

Some of this is read-only after load, especially scripts and base tables. Some is mutable or save-state-related:

- Event objects are mutable and saved/loaded.
- Scene/object/player role state is at least partly mutable and stored in save files.
- Script entries are read-only after loading.
- Store/enemy/enemy-team/magic/battlefield/level-up tables look mostly read-only.

Current save load/save paths allocate an entire `SAVEDGAME_DOS` or `SAVEDGAME_WIN` object. Actual save files in this data directory are about 184KB to 189KB. That transient allocation is too large for SRAM.

The checked embedded save slice is `embedded/pal_save_cache.c`: it reads real `.rpg` files into `pal_psram_save_state`, validates the file fits that fixed buffer, exposes common little-endian header fields, and writes a byte-preserving round trip from the same fixed buffer without allocating a full save object.

### Video and Frame Buffers

In SDL2 mode, `VIDEO_Startup()` creates:

- `gpScreen`: 320x200 8-bit surface, about 64KB pixels.
- `gpScreenBak`: another 64KB pixels.
- `gpScreenReal`: 320x200 32-bit surface, about 256KB pixels.
- `gpTexture`: streaming ARGB8888 texture, likely another about 256KB backing store, depending on backend.
- `gpPalette`: small.

Battle adds:

- `g_Battle.lpBackground`: compatible 8-bit surface, about 64KB.
- `g_Battle.lpSceneBuf`: compatible 8-bit surface, about 64KB.

The desktop SDL2 render path alone exceeds fast SRAM. For the target, the expert should consider whether `gpScreenReal` and/or `gpTexture` can be removed, line-converted, placed in PSRAM, or replaced by direct indexed-to-display output.

### Current Scene Resource Residency

`PAL_LoadMap()` allocates:

- `PALMAP`: host `sizeof` about 65,552 bytes, dominated by `DWORD Tiles[128][64][2]`.
- `pTileSprite`: raw `GOP.MKF` chunk for current map, up to about 65KB.
- Temporary compressed `MAP.MKF` input buffer during load, up to about 23KB in this data set.

`PAL_LoadResources()` then loads every event object sprite in the scene from `MGO.MKF`, one allocation per event object. It does not deduplicate repeated sprite numbers. It also loads player walking sprites.

### Temporary Buffers and Stack Risk

Several files use `PAL_LARGE` local arrays. On Unix this macro is empty, so these are stack allocations:

- `battle.c`: 64KB local background buffer.
- `ending.c`: often two 64KB local buffers.
- `uigame.c`: status/equipment screens can allocate 64KB + 64KB + smaller buffers locally.
- `text.c`: 64KB local face buffer.

Some existing console ports define `PAL_LARGE static`, but a static buffer still consumes RAM. On this target, these should become named static buffers with fixed SRAM/PSRAM placement.

Other temporary peaks:

- `PAL_MKFDecompressChunk()` allocates a compressed input buffer every time, then decompresses into the caller's destination. This can transiently double memory for a chunk. Largest compressed sprite/effect chunks are around 34KB to 37KB.
- `PAL_RNGPlay()` allocates two 65,000-byte buffers for cutscene frames. The measured maximum RNG frame decompressed size is 64,288 bytes; total predecoded RNG frame payload across all movies is about 7.3MB.
- Splash screen allocates one 128KB heap buffer and two extra compatible surfaces.
- `SOUND_Play()` loads each sound-effect chunk into heap and keeps it until playback finishes. Largest `VOC.MKF` chunk is about 52KB.
- The current embedded slice proves the replacement shape for sound effects: host-converted PCM16 SFX chunks, no runtime allocation, fixed `pal_psram_sfx_bank`, a small static `pal_sfx_` metadata table, and mixing into `pal_sram_audio`. It has only been smoke-tested on selected real chunks so far, not wired into the full engine mixer.
- The current embedded menu/status slice proves the replacement shape for menu background/image/box scratch buffers with named PSRAM arrays instead of `PAL_LARGE` stack arrays or heap buffers.
- The current embedded ending/splash slice proves the replacement shape for ending FBP screen buffers and ending sprite assets with named PSRAM arrays plus read-only sprite views.
- The current embedded palette/fade slice proves the replacement shape for palette transition scratch buffers with named SRAM arrays instead of `PAL_LARGE SDL_Color[256]` local buffers.
- Audio output creates a mix buffer sized by sample count, channels, and sample size. Default is 1024 samples, stereo, 16-bit, about 4KB.

## Current Code Has No Memory Tiers

Current code generally uses:

- `malloc`, `calloc`, `realloc`, `free`.
- `UTIL_malloc` and `UTIL_calloc`, thin wrappers around libc allocation.
- SDL surface/texture allocation.
- `FILE *` and `fseek`/`fread` for all archive access.

There is no existing allocator interface for "fast SRAM vs PSRAM", no asset cache abstraction, and no NOR memory-mapped read abstraction.

## Why Pre-Decompression Is Attractive but Needs Scope

Pre-decompression can help by:

- Removing YJ1/YJ2 decode CPU cost at runtime.
- Removing compressed-input scratch allocations.
- Letting read-only sprite/map/script data live in NOR if addressable there.
- Allowing a simpler runtime-native packed format with direct offset tables.

But full pre-decompression is too large for 16MB NOR:

- All map tile data alone is 14.6MB.
- GOP raw tile sprites are 11.5MB.
- All major decompressed YJ1 graphics total over 26MB before GOP.

Therefore, the interesting design space is probably one of:

- Keep full original data on TF only for host-side conversion and verification.
- Build generated resource packs where every runtime payload is already raw/native.
- Put hot read-only raw/native data in NOR and large sequential raw/native data in TF.
- Convert assets into a more compact runtime-native format, not necessarily raw decompressed bytes.
- Deduplicate scene sprites and store read-only decompressed sprite chunks once.
- Keep large read-only tables in NOR and only mutable state in SRAM/PSRAM.
- Convert fonts/text into a target-specific subset/indexed format.

# SDLPAL on 300KB SRAM / 8MB PSRAM / 16MB NOR / TF: Memory and Asset Architecture

## 0. Assumptions (stated up front, since the design hinges on them)

1. **NOR is memory-mapped and byte-addressable** with CPU-cached reads (XIP-style), giving effective random read throughput in the 10–40MB/s range for cache-line-sized accesses. If NOR is *not* mappable, the design degrades gracefully: every "blit/point directly from NOR" below becomes "copy into a PSRAM pin cache at scene load," which the PSRAM budget comfortably absorbs.
2. **Executable code shares the 16MB NOR.** I budget 2.0MB for code + rodata + reserve. If code lives elsewhere, everything gets easier.
3. **PSRAM** is CPU-cached, ~20–80MB/s effective, safe for frame-rate-scale bulk operations (64KB/frame copies) but wrong for the hottest inner loops (per-pixel tile blitting, wave effect).
4. **Display** takes RGB565 (or similar) via scanline/DMA pushes; no hardware indexed-color scanout. DMA buffers may need to be in internal SRAM — I budget small line buffers for that.
5. **Saves are written to TF only.**
6. **Required features:** RNG cutscenes, RIX/OPL music, VOC sound effects, save/load. **Not required:** AVI, MP3/OGG/OPUS, TinySoundFont, touch overlay, GLSL shaders, high-quality resampling, Win95/YJ2 data support (this port targets the DOS/YJ1 set only).
7. **Hard implementation constraints from the owner:** no runtime `malloc` family; no runtime decompressor; all target memory is explicit static `uint8_t` SRAM/PSRAM storage or `const uint8_t` read-only pack data; native SDL remains the verification harness.

## 1. The two decisions everything else follows from

**Decision A: all runtime resource data is predecoded before pack creation.** The target runtime must not link YJ1/YJ2/LZ4/etc. decoders. The critical observation for sprites still holds: "YJ1-decompressed" PAL sprite data is already the RLE format the blitter consumes in place. Once decoded by the host pack builder, sprites need zero RAM residency if they are in NOR: `PAL_LoadResources()` and battle loading become pointer-table construction. This collapses your worst walking scene from ~909KB of scene-resident RAM to the map/GOP working set, and collapses battle sprite loading to read-only pointer setup.

**Decision B: data too large for NOR goes to a TF resource pack, still predecoded.** GOP is already raw and is exactly one <=65KB chunk per scene. MAP is 14.6MB after decode and is also one 64KB chunk per scene. RNG predecoded frames total about 7.3MB and are sequential by construction. These assets should live in TF as raw/native chunks and be read into fixed buffers at scene/cutscene boundaries, not decompressed at runtime.

Everything else falls out of these two decisions.

## 4. Asset pipeline and pack format

Extend `Consult/mkf_audit.py` into a build tool that produces two pack images with an identical TOC format:

- `pal_nor.pak` — flashed to NOR, mapped at a fixed address.
- `pal_tf.pak` — copied to the TF card (FBP, GOP, MAP, RNG, generated PCM SFX bank).

Format: a header (magic, version, archive count), then per-archive chunk tables of `{u32 offset, u32 size, u8 format, u8 flags}` with 4-byte alignment, then payload. There is no runtime codec field: every payload is `RAW` or a target-native structure/image/sprite format. The NOR pack's TOC costs zero RAM because it is itself NOR-mapped; the TF pack's TOC is copied into a fixed PSRAM table at boot so TF is never seeked for index lookups.

Build-time steps: YJ1-decompress every MAP/FBP/MGO/ABC/F/FIRE/RNG frame that the runtime will consume; store the decoded bytes in NOR or TF packs; convert SSS/DATA chunks to target-native struct layout with endianness fixed and any runtime data fixups baked in; build the font/text pack (§6); convert VOC chunks to the output sample format (§7); emit a manifest with sizes so NOR overflow is a build error, not a runtime surprise. Crucially, add a verification mode: decode every converted asset and byte-compare against the desktop SDLPAL decode path, so the pipeline is provably lossless before any target work begins.

Assets that do not fit in NOR are still decoded/native in the TF pack. If a future data set pushes NOR over budget, the demotion order is decoded FBP to TF, decoded FIRE to TF, then less-hot UI/faces/icons to TF. Do not demote anything to a compressed runtime format.

## 5. Scene and battle loading

Scene load becomes: read the decoded MAP chunk from NOR/TF into the fixed PSRAM 64KB tile table; read the GOP chunk from TF into the fixed PSRAM copy and memcpy into the SRAM big slot; walk the scene's event objects and fill a table of `{const uint8_t *sprite_ptr, uint32_t size}` pointing into NOR-mapped decoded MGO, or into a fixed PSRAM sprite-pin buffer if a TF-backed fallback is selected. Deduplication by sprite number becomes a pointer-table concern rather than a memory one, but still do it. Do not copy per-frame sprite data into SRAM; frames are blitted from read-only pack data or the explicit PSRAM pin buffer directly.

Keeping the map *tile table* (the 64KB `Tiles[128][64][2]` array) in PSRAM is fine: per frame you read ~200–400 8-byte entries, trivial bandwidth. Do not transform it for flash access; it's per-scene mutable-adjacent working data and PSRAM is the right tier. The tile *pixels* (GOP) are the hot data and get the SRAM slot.

Battle load becomes: set player sprite pointers into decoded NOR F data; set enemy sprite pointers into decoded NOR ABC data (worst team 385 costs zero RAM instead of 92KB); read one decoded FBP background from NOR/TF into a fixed PSRAM 64KB buffer; repoint the scene buffer at the SRAM big slot (the map is not drawn during battle); effect sprites are NOR pointers if FIRE is in NOR, or raw chunks read into a fixed PSRAM effect buffer if FIRE is TF-backed. There is no runtime effect/background/map decompression path.

## 6. Font and text

The 2.1MB `unicode_font[65536][32]` plus width/offset arrays must go entirely. At build time, scan `WORD.DAT`, `M.MSG`, item/magic/name strings, and the engine's built-in UI strings for the set of codepoints actually used — for the DOS Chinese data set expect roughly 2,500–3,500 distinct characters. Emit a NOR pack of `{sorted u16 codepoint array, per-glyph 32-byte bitmap, per-glyph width byte}`: ~110–130KB, fully read-only, zero RAM. Lookup is a 12-step binary search per glyph; if that ever shows up in profiles, add a 256-entry first-level page table, but it won't. The runtime `font_offset_x/y` allocations disappear; offsets are baked per-glyph at build time.

Preconvert all text to UTF-16 (or, slightly better, directly to glyph indices into the font pack) at build time, stored as an offset table plus string data in NOR. `PAL_InitText()` then just maps pointers instead of converting encodings and heap-allocating every string. This removes the conversion code, the wide-string heap, and the transient load spike, and it makes the font-subset guarantee airtight: the font pack and text pack are built from each other.

The checked implementation slice is `embedded/pal_text_cache.c`: `tools/pal_pack_build.py` converts `WORD.DAT` and `M.MSG` from CP950 to UTF-16LE before writing the NOR pack, and runtime only validates offset tables and returns `const uint8_t *` spans. This is not the final glyph-index format, but it proves the no-heap/no-runtime-codepage-conversion direction on the real corpus.

The checked font slice is `embedded/pal_font_cache.c`: `tools/pal_pack_build.py` converts `WOR16.ASC`/`WOR16.FON` into one read-only FONT payload in the NOR pack. The current audited data yields 2,600 unique CJK glyphs, 83,200 bytes of glyph data, and an 88,432-byte chunk including the header and codepoint table. Runtime maps the chunk as `const uint8_t *` data, validates it, and binary-searches codepoints without allocating. ASCII is intentionally outside this WOR16 CJK pack and should continue through the compact ASCII font path or a final unified font index.

## 7. Audio

Pick one output rate (22,050Hz or 32,000Hz, 16-bit) and configure the OPL core to synthesize at that rate directly, eliminating the resampler and its 147KB of static float LUTs — delete `resampler.c` from the target build entirely. Disable MP3/OGG/OPUS/AVI/TinySoundFont/surround at compile time. RIX data lives in NOR; the OPL emulator's working state is a few KB in SRAM.

VOC effects: convert at build time to the exact output format (rate-converted, sign-converted, mono s16 or s8) so runtime playback is a pure mix loop with no per-sample conversion. The current generated 22050Hz mono PCM16 SFX archive is 9.2MB, too big for NOR and not something to assume is fully resident in PSRAM. It lives on the TF pack; the fixed PSRAM SFX array holds selected boot-critical sounds or scene/battle prefetches. `SOUND_Play()` becomes "point the mixer at a known PSRAM span"; it must not allocate.

The checked implementation slices are `embedded/pal_sfx_cache.c` and `embedded/pal_audio_static.c`: the pack builder converts VOC chunks to 22050Hz mono PCM16 in the TF-backed SFX archive, selected chunks are copied into the normal static `pal_psram_sfx_bank` array from either a mapped pack or file-backed read-at callback, and `PalAudio_MixSfx()` mixes them into `pal_sram_audio`. This is intentionally simple static storage, not a pool, and it avoids linking the desktop resampler in the embedded slice. Current real-data smoke coverage checks chunks 1, 62, 192, 213, 214, 255, and 272, including a converted 211,152-byte chunk from VOC #255.

## 8. Decompression

There should be no decompressor in the target runtime. Delete or exclude YJ1/YJ2/LZ4/etc. decode code from the embedded build. `PAL_MKFDecompressChunk()` should not exist in the target resource path; the replacement asset API should expose only already-decoded/native chunks.

Runtime validation should reject any pack whose TOC says a chunk needs decoding. Build validation should also fail if decoder symbols are linked into the embedded/native-verification binary. The host pack builder is the only place where YJ1 decode is allowed.

## 9. Video

For the embedded backend, delete `gpScreenReal` and `gpTexture` (that's ~512KB of the desktop path gone). The engine keeps exactly one 8-bit 320x200 framebuffer in SRAM; at scanout, convert per scanline through a 256-entry palette-to-RGB565 LUT (512 bytes, SRAM) into small double-buffered line buffers pushed by DMA. Palette fades become LUT rewrites, not framebuffer work. Keep `gpScreenBak` if needed for fades/transitions, but put it in a fixed PSRAM buffer. Battle's background buffer stays in PSRAM; the battle scene buffer takes the SRAM big slot as described. Replace all `PAL_LARGE` stack buffers (`battle.c`, `ending.c`, `uigame.c`, `text.c`) with named static buffers, not heap/scratch allocations.

The checked static video slice is `embedded/pal_video_static.c`: it clears and saves/restores `pal_sram_framebuffer` through `pal_psram_screen_bak`, keeps a 512-byte `pal_video_rgb565` LUT, and converts one indexed scanline at a time into `pal_sram_display_dma`. The native SDL smoke still wraps the 8-bit SRAM framebuffer for host verification, but project-side code no longer needs a 32-bit full-screen backing buffer in this slice.

## 10. Code-change plan and sequencing

Do not add a tier allocator. Declare named `uint8_t` arrays for SRAM and PSRAM buffers, and use named `const uint8_t` or typed `const` views for NOR/pack data. Every buffer has a compile-time size, an owner, and a lifetime. The native SDL build should use the same declarations so desktop tests catch overflows before target work.

The asset API replaces all `FILE*`/MKF paths: `ASSET_MapConst(archive, chunk, &size)` for NOR-backed read-only chunks, `ASSET_ReadRaw(archive, chunk, dst, dst_capacity)` for TF-backed raw chunks, and typed helpers for target-native tables. There is no `ASSET_LoadDecoded()` on the target because no target chunk should need decoding.

Sequence, highest risk-retirement first:

1. **Build the asset pipeline with byte-exact verification** against desktop SDLPAL decoding. It must emit only raw/native runtime payloads.
2. **Add native SDL fixed-memory harness:** project code uses static SRAM/PSRAM arrays, pack data is mapped read-only, and wrappers/traps fail the test on `malloc`, `calloc`, `realloc`, or `free` from project code.
3. **Target microbenchmarks before porting anything:** memory-mapped NOR random/strided read throughput using a replayed real sprite access trace, PSRAM memcpy/memset rates, TF sequential read rate, LCD push rate.
4. **Static buffer declarations + PAL_LARGE removal**, on desktop, with direct checks for the named arrays before target bring-up. The current embedded slices already prove this shape for scene, battle, RNG, SFX, and global-data residency, but the full engine path still needs the same conversion.
5. **Asset API cutover** on desktop, reading the packs via `mmap` with `PROT_READ` so any write to "NOR" data faults. The runtime should reject any unsupported or non-native chunk format.
6. **Font/text conversion** (desktop-verifiable, removes the single biggest static blocker).
7. **Video backend** (8-bit FB + scanline convert) and **audio simplification** (fixed rate, no resampler, VOC bank/prefetch).
8. **Artifact checks:** `size`, `objdump -h`, `objdump -t`, `nm -S --size-sort`, and linker map checks enforce `.text`, `.rodata`, `.data`, `.bss`, named `pal_sram_*`/`pal_psram_*` symbol totals, and NOR budgets. The same checks should assert decoder symbols are absent.
9. **Target bring-up:** title -> walking scene -> scene transitions across scenes 156/59/65 -> battle team 385 -> heaviest FIRE magic -> RNG opening -> save/load round-trip.
10. **Performance pass:** enable the PSRAM sprite pin cache if step 3 or 9 shows NOR blit stalls.

Acceptance tests: golden-frame CRCs of `gpScreen` at scripted checkpoints compared against desktop SDLPAL on the same data; a scripted walk touching the five audited worst scenes with static-buffer usage logs; battle entry/exit including SRAM big-slot restore verification (CRC the GOP chunk after battle); full predecoded RNG playback without underflow of the read-ahead ring; save->reload->byte-compare of save-state tables; audio underrun counter must read zero across a full battle with music plus concurrent SFX; native SDL artifact checks must show no project-side heap calls and no target decoder symbols.

## 11. Risk list

- **NOR blit bandwidth (top risk).** Per-frame sprite reads from mapped NOR at ~2–4MB/s effective demand should be fine, but XIP cache contention with code fetches is hardware-specific. Mitigation is cheap and pre-planned: dedup-keyed PSRAM pinning of the current scene's sprites (<812KB worst case, ~2.7MB free). Retire this risk in step 2, not step 7.
- **PSRAM in hot loops.** The framebuffer, wave effect, and tile blit source must never land in PSRAM; the static buffer map plus native-SDL assertions should guard this. Battle's 64KB/frame PSRAM composites are within budget but should be watched at high battle speed settings.
- **Static buffer lifetime bugs.** Without `malloc`, memory pressure is controlled, but reusing a fixed buffer in the wrong mode can corrupt state. Keep reuse explicit by variable name, and make tests cover field, battle, menu, RNG, save/load, and audio buffer lifetimes.
- **TF latency visibility.** Scene transitions now read decoded MAP plus GOP, usually about 128KB total, which is still sequential and acceptable but must be measured. RNG needs the read-ahead ring sized against measured TF throughput; SFX latency is eliminated only if the fixed PSRAM bank is loaded at boot or a scene/battle prefetch policy is complete. Save writes may pause visibly.
- **No runtime decompression fallback.** This is intentional, but it shifts all correctness risk to the host pack builder. The pack manifest must record source file hashes, decoded sizes, and verification status; the target must reject packs with compressed/runtime-codec flags.
- **Mutable state mixed with read-only data.** Event objects, scene table, object table, and player roles are save state and must be fixed PSRAM copies of NOR templates — the current `PAL_InitGlobalGameData()` load-everything-as-one-heap pattern must be split along exactly this line. Scripts and DATA tables are believed read-only after load, but SDLPAL applies some load-time fixups for the DOS data version; these must be baked at build time, and the `mmap(PROT_READ)` desktop harness will catch any residual runtime writes as faults before they become silent NOR no-ops on target.
- **Struct layout/endianness drift** between the Python build tool and the target ABI for the native-format SSS/DATA chunks — covered by the byte-exact verification mode plus golden-frame tests.
- **Audio realities:** OPL synthesis CPU cost at the chosen rate needs measurement (fallback: lower rate or mono), and the audio DMA path may require buffers in internal SRAM — budgeted, but confirm the SoC's DMA-addressable regions before placing the SFX mixer's staging buffers.
- **Boot-time PSRAM SFX bank load** (~1–2s) may be unacceptable UX for some products; fallback is lazy per-scene SFX prefetch into fixed buffers, which the TF TOC-in-PSRAM design already supports.
- **Build artifact drift.** A native SDL smoke test can pass while `.bss`, `.data`, `.rodata`, or forbidden symbols exceed target limits. Treat `size`, `objdump`, `nm`, and linker-map checks as required tests, not diagnostics.

The single most load-bearing unknown is assumption 1. Confirm NOR mappability and measured read behavior first; every other element of this plan survives either answer, but the answer decides whether the sprite tier is "NOR, zero RAM" or "NOR-sourced PSRAM pin cache, ~1MB."
