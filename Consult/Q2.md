# Consultation Q2: Full-Game CoreS3 SE Port Strategy Without Rewriting PAL Logic

## Ask

Please review the current SDLPAL embedded-port direction and recommend the safest architecture for reaching the **full original game loop** on **M5Stack CoreS3 SE** without reimplementing or approximating PAL game logic.

This note is for an expert with **zero prior knowledge** of this codebase. It should be read as a continuation of `Consult/Q1.md`, but it is self-contained and restates the important background.

The key problem has changed since Q1:

- Q1 was mainly about memory placement, offline asset conversion, and feasibility under 300KB SRAM / 8MB PSRAM / 16MB NOR.
- Q2 is about **how to get from a hardware/resource bring-up scaffold to the real SDLPAL engine without semantic drift**.

The concern is not whether we can draw a scene. We already can. The concern is that an earlier attempt started adding target-side script/game behavior directly in the CoreS3 SE app, which is the wrong direction because it duplicates or simplifies real PAL logic.

Please answer these questions:

1. Should the next step continue the current compile-time `PAL_NO_RUNTIME_HEAP` / `PAL_NO_RUNTIME_DECOMPRESS` full-engine path, or should the project define a cleaner new resource/platform abstraction and move the original engine behind it?
2. How should the port preserve original behavior in `script.c`, `scene.c`, `res.c`, `battle.c`, `uigame.c`, `fight.c`, and related files while still enforcing fixed memory and offline-generated assets?
3. What verification strategy on native SDL2 would best prove that the embedded/static-buffer path still behaves like normal SDLPAL before flashing CoreS3 SE hardware?
4. What checks should be added so that "no malloc, no runtime decompression, static named buffers only" remains enforceable while the real game loop comes back?
5. Is the current SRAM/PSRAM/NOR/TF placement reasonable, or are there obvious misplacements that should change before further integration?

## Non-Negotiable Constraints

These are not open design questions.

- Target board is **M5Stack CoreS3 SE**, not CoreS3.
- Fast SRAM: **300KB total**.
- PSRAM: **8MB total**, much slower than SRAM.
- NOR flash: **16MB total**, read-only at runtime, random accessible.
- TF card: effectively unlimited capacity, but slow.
- Current PAL data set path:

```text
/mnt/hgfs/deb13/PAL
```

- Runtime allocation rules:
  - no `malloc`
  - no `calloc`
  - no `realloc`
  - no `free`
  - no C++ `new`
  - no C++ `delete`
- No memory-pool abstraction. Use normal named static variables and arrays.
- Runtime storage should be explicit:
  - `uint8_t` arrays for SRAM/PSRAM buffers
  - `const uint8_t *` or typed `const` views for read-only NOR pack data
- No runtime decompression. YJ1/YJ2/VOC/text/font conversion belongs only in host-side build tools.
- TF resource-pack and save-file I/O should use ESP-IDF FatFS.
- The native SDL build should stay usable as a verification harness.
- Resource usage should be checked from ELF/build artifacts with `size`, `objdump`, `nm`, linker maps, and pack checks.
- No OGG/OPUS/MP3/AVI support is needed for the current data set.
- No target audio for now. The CoreS3 SE target app should not link `pal_audio_static.c` / `pal_sfx_cache.c` or reserve the SFX bank until hardware playback is in scope.

## What Q1 Already Established

Q1 already covered the main memory/asset feasibility result:

- Full pre-decompression into 16MB NOR is not feasible.
- The correct direction is host-side conversion into runtime-native packs.
- Hot read-only generated assets can live in NOR.
- Large generated native assets must live in TF-backed packs.
- Runtime should copy only current working-set resources into named static SRAM/PSRAM buffers.
- Runtime should map read-only assets as `const uint8_t *` where possible.
- The native SDL path should be used to verify the static-buffer design before target deployment.

The current accepted storage shape is:

- **NOR pack**: hot read-only generated assets.
- **TF pack**: large generated native assets.
- **PSRAM**: large mutable working sets, save state, scene staging, pinned sprites, RNG frames, FBP staging, menu scratch.
- **SRAM**: indexed framebuffer, tiny palette scratch, LCD DMA scratch, other hot small buffers.

## Why the Desktop Path Cannot Simply Be Reused As-Is

The need for contract/static-buffer work is not theoretical. Q1 already identified several current desktop-era memory problems:

- `fontglyph.h` keeps a mutable `unicode_font[65536][32]` table: about `2MB`.
- The same font path also carries additional width/offset tables.
- `resampler.c` has about `147KB` of mutable float LUTs.
- `global.c` heap-loads the main PAL global/script data set at roughly `532KB` on this corpus.
- Desktop save/load allocates roughly `184KB` to `189KB` per save operation for this corpus.
- Worst measured normal scene residency was about `909KB` before deduplication and before counting several other buffers.
- The same scene subset drops to about `143KB` after event-sprite deduplication, which is why sprite dedup/pinning matters.
- Several legacy paths use `PAL_LARGE` 64KB scratch buffers or allocate full-screen temporary surfaces.

So the embedded-port problem is not just "replace SDL". The desktop engine assumes resource shapes and temporary memory use that do not fit the CoreS3 SE rules without structural replacement underneath the original logic.

## The Actual Design Problem

The project now has enough evidence that fixed buffers, generated packs, and CoreS3 SE hardware access are viable.

The real question is how to restore the game safely.

Two broad directions are possible:

### Direction A: Keep the Original Engine Logic, Replace Subsystems Under It

This means:

- preserve original game logic in `script.c`, `scene.c`, `res.c`, `battle.c`, `fight.c`, `uigame.c`, and related files
- continue adding embedded-safe contract paths under compile-time flags
- replace resource acquisition, scratch buffers, save I/O, video pixel storage, and platform glue
- let original functions remain the source of truth for behavior

Benefits:

- least semantic drift
- easier to compare against standard desktop SDLPAL
- avoids inventing a second PAL interpreter

Risks:

- contract branches inside original files can become hard to reason about
- original code has many hidden assumptions about mutable buffers, surfaces, timing, and resource lifetimes
- if the resource/platform abstraction remains too ad hoc, maintenance cost will grow

### Direction B: Build a New Target Runtime on Shared Static Resource APIs

This means:

- keep static pack/cache/resource slices
- keep platform code in ESP-IDF
- gradually rebuild gameplay behavior in a new runtime that consumes the static slices

Benefits:

- clearer target-specific control
- no need to preserve desktop-era layering

Risks:

- very high semantic drift risk
- duplicated gameplay logic
- enormous testing burden
- likely endless opcode and edge-case chase in scripts, battle flow, UI flow, save flow, and event logic

The recent revert is strong evidence that Direction B is the wrong path for this project unless there is a very compelling reason the original engine cannot be preserved.

## Current Working Hypothesis

The current implementer-side hypothesis is:

1. Freeze `esp32s3/main/app_main.c` as a hardware/resource smoke app only.
2. Stop adding more gameplay or script behavior there.
3. Push the real effort into the native SDL2 contract full-engine path.
4. Make that contract path run more and more of the original SDLPAL loop using generated packs and static buffers.
5. Add strong comparisons against normal desktop SDLPAL.
6. Once the contract path is trustworthy, reuse that same engine/static-resource path on CoreS3 SE and keep the ESP-IDF side narrow: LCD, touch, FatFS, pack mapping, timing, and audio later.

Please critique this plan.

# Q2 Response: Restoring the Full Original Game Loop Under the Contract

## 1. The core recommendation

Your working hypothesis is correct and the revert was the right call. Direction B fails for a reason that is structural, not just effort-based: PAL's observable behavior is not specified anywhere except in the original C. There are 42,494 script entries whose semantics depend on exact interpreter behavior, including edge cases, failsafe branches, and order-of-mutation details in `script.c`. Any reimplementation is a specification-recovery project with no oracle other than the code you declined to run. Direction A keeps the oracle as the implementation.

But I want to sharpen Direction A beyond "keep adding contract flags," because the stated risk — contract branches metastasizing inside original files — is real. The refinement is:

**Prefer link-time substitution at existing seams over compile-time branching inside game-logic files.** SDLPAL already has a de facto porting layer: `palcommon.c` (MKF access/decompression), `util.c` (allocation, file open), `video.c`, `input.c`, `audio.c`, and the `palcfg`/platform glue. The game-logic files (`script.c`, `scene.c`, `fight.c`, `battle.c`, `uigame.c`, `ui.c`, `res.c`, `global.c`) call these layers through stable function signatures. The contract build should compile the game-logic files **unmodified where possible**, and link them against pack-backed implementations of the same signatures:

- `PAL_MKFGetChunkSize` / `PAL_MKFReadChunk` / `PAL_MKFDecompressChunk` → pack-reader implementations. For archives stored decompressed in the pack, "decompress chunk" degenerates to "return pointer or copy span." No YJ1 code links; the *name* survives, the *behavior contract* (caller gets the decoded bytes) survives, and every call site in battle/fight/rngplay/res compiles untouched.
- `UTIL_malloc` / `UTIL_calloc` in resource-loading paths → per-call-site conversion to named statics or const views (this one does require touching `res.c`/`global.c`, see below).
- `FILE*` save I/O → the `pal_save_cache` buffer + FatFS backend behind the existing save entry points.
- SDL surface usage → a minimal surface shim (§5).

Where the original files genuinely must change — `res.c`'s per-object sprite ownership, `global.c`'s load-time allocation, `PAL_LARGE` scratch — make the change **unconditionally, for all builds**, in a form the desktop build also uses. "Desktop runs on the embedded resource layer" is a far stronger invariant than "embedded build tolerates the desktop layer," because then there is only one resource layer to reason about and the differential tests exercise the same code you'll ship.

Concretely, adopt a **divergence budget**: an explicit, CI-enforced list of original engine files allowed to differ from their pre-port state, with a one-line justification each. Expect the list to be roughly: `res.c` (sprite storage becomes const views/pin-cache handles), `global.c` (game-data init reads PSRAM copies + NOR views instead of heap-loading; endian/fixup code moved to build time), `text.c` and `font.c` (replaced by cache-backed equivalents), `video.c`/`input.c`/`audio.c` (platform layer, expected), plus `PAL_LARGE` sites in `battle.c`/`ending.c`/`uigame.c`/`text.c` converted to named static scratch. If a milestone requires touching `script.c`, `fight.c`, or `scene.c` beyond mechanical seam changes, treat that as a design alarm, stop, and re-examine the seam.

On the scaffold: yes, freeze `esp32s3/main/app_main.c` as a board/pack/display smoke test permanently. Its final fate is to be *replaced* by the engine's `main`, not to grow toward it. Similarly, demote `pal_script_static.c` from "runtime component" to "verification tool" — its bounded tracing is useful for the differential harness, but it must never sit in the runtime call path once the real `PAL_RunTriggerScript` is linked.

## 2. Answering the five questions directly

**Q1 — continue the contract path or build a cleaner abstraction first?** Continue, with the link-seam discipline above. Do not pause for a grand abstraction redesign; the abstraction you need already exists as SDLPAL's own layering plus your `embedded/` slices. The one piece of *deliberate* new abstraction worth building before restoring more gameplay is the determinism harness (§4), because every later milestone depends on it and retrofitting determinism after battle integration is much more painful.

**Q2 — how to preserve original behavior while enforcing fixed memory?** The rule is: replace *storage and acquisition*, never *control flow or state mutation*. `PAL_LoadResources()` keeps its exact load ordering, its free-before-load sequencing, and its per-event-object iteration; only the innermost "get me the decoded bytes for MGO chunk N" changes, returning either a NOR const pointer or a pin-cache slot. `PAL_RunTriggerScript`/`PAL_RunAutoScript` compile as-is; a target-side script executor should be treated as a design error, full stop — including "just a few opcodes for previews." The subsystems that can be safely swapped underneath script execution are exactly the ones scripts observe only through side effects the engine itself mediates: resource reads, pixel storage, palette application, save serialization, input polling, and the clock (virtualized, §4). The subsystems scripts observe *directly* — event object table, party/role state, object table, scene table, script-entry table — must keep their exact in-memory layout and mutation order, which is why they live as PSRAM copies with original struct definitions rather than any re-modeled form.

**Q4 — enforceability checks:** §6 below.

**Q5 — placement review:** §5 below.

## 3. Staged plan with milestones

Each milestone has an explicit gate; do not start the next before the gate passes.

**M0 — Freeze and fence (days).** Freeze the scaffold. Land the divergence-budget CI check (diff of game-logic files against a recorded baseline; fail on unlisted drift). Land the PROT_READ NOR simulation in the native contract build: `mmap` the NOR pack read-only so any engine write into "read-only" data faults immediately. This is your cheapest and highest-value semantic tripwire, and it will almost certainly fire during M1–M2 (§7 explains where).

**M1 — Determinism harness on stock desktop SDLPAL (1–2 weeks).** Before touching the contract build further, make *unmodified* desktop SDLPAL deterministic under a `PAL_DETERMINISTIC` mode: seeded RNG, a virtual frame-counter clock replacing `SDL_GetTicks()`-derived timing at the existing delay/tick seams, and record/replay input injected at the `input.c` event boundary. Add checkpoint emission: per-frame CRC of `gpScreen` after present, a script-trace ring (script entry index, opcode, event-object id) hashed per frame, and save-state serialization hashes at scene transitions. Record golden traces for scripted routes: intro → first town walk → shop/dialog → save; a route through your audited worst scenes (156/59/65); several battles including team 385; the opening RNG cutscene. This is the oracle. It's built against stock SDLPAL precisely so it measures the contract build against unmodified behavior.

**M2 — Full engine boots in the contract profile (2–4 weeks).** Link the real `main.c` loop in `EMBEDDED_CONTRACT=1`: pack-backed MKF layer, PSRAM-copy global data, const-view scripts/DATA, cache-backed font/text, static-surface video. Gate: title screen and main menu render, golden framebuffer CRCs match stock for the pre-gameplay route, zero forbidden-symbol hits, zero PROT_READ faults (after fixing whatever fires — see §7).

**M3 — Walking gameplay parity (2–4 weeks).** Scene load through the real `PAL_LoadResources`, script execution through the real interpreter, dialogs, menus, save/load through the static save buffer. Gate: the town/dialog/save golden route replays with matching framebuffer CRCs, matching script-trace hashes, and byte-identical save output versus stock desktop (modulo any deliberately re-specified save container fields — ideally none; keep the original save format so saves are cross-checkable).

**M4 — Battle parity (2–3 weeks).** Real `battle.c`/`fight.c` over `pal_battle_cache` storage. Battle is the most timing- and RNG-entangled subsystem; the virtual clock and seeded RNG from M1 are what make this tractable. Gate: recorded battle routes replay with matching trace hashes and end-of-battle save-state hashes.

**M5 — RNG cutscenes, ending, full-route replay (1–2 weeks).** Gate: opening cutscene frame checkpoints match; a long mixed route (multi-scene, battles, saves, cutscene) replays end-to-end with zero divergence.

**M6 — Target hosting (2–4 weeks).** Move the engine core to ESP-IDF. The ESP-IDF side contributes only: board init, LCD flush from `pal_sram_framebuffer`, touch→input-event mapping at the same `input.c` seam the replay harness uses, FatFS pack/save I/O behind the same read-at interface, and the clock source. Gate: the same golden routes replay *on hardware* via the record/replay path with matching trace and save hashes (framebuffer CRCs comparable because the engine-side framebuffer is identical pre-scanout), plus stack high-water and frame-time measurements.

**M7 — Performance and then audio.** Only now tune: SRAM tile slot, dirty-rect scanout, sprite pin policy. Audio re-enters afterward with its own budget review.

One deliberate insertion: run a **target performance smoke early**, around M2–M3, not waiting for M6. Take the already-working scaffold, drive the real `PAL_MakeScene` draw path (map layers + sorted sprites from NOR/PSRAM into the SRAM framebuffer) on a real loaded scene, and measure frame time. Semantic parity work is wasted if the draw path lands at 6fps; you want that data while placement decisions (§5) are still cheap to change.

## 4. Verification details worth being specific about

Compare, in priority order: **script-trace hashes** (highest diagnostic value — divergence localizes to an opcode and entry index), **save-state bytes** at transitions (catches silent state drift that doesn't render), **framebuffer CRCs** per frame (catches rendering/palette/timing drift, but a CRC mismatch alone tells you little — keep the failing frame's PNG dump from both builds), **scene-entry checkpoints** (scene id, party position, event-object table hash on every enter/teleport), **battle transition records** (team id, initial state hash, outcome hash), and **RNG cutscene frame CRCs** at fixed frame indices. Menu/dialog flows are covered adequately by framebuffer CRCs plus input replay; they don't need bespoke checkpoints.

Two harness rules that save weeks: first, when a divergence appears, the harness should bisect *within the route* automatically (first diverging frame, then dump both script-trace rings around it). Second, keep golden traces version-pinned to the pack manifest hash — a pack rebuild that changes any payload byte must invalidate goldens, otherwise you'll chase phantom regressions.

Also run the native contract build periodically under ASAN/UBSAN in a separate profile (sanitizers and `--wrap` interact awkwardly; it's fine for this profile to relax the wrap checks — its job is memory-safety of the new seam code, not contract enforcement).

## 5. Buffer placement review

The current placement is fundamentally sound. Specific notes:

**SRAM (78KB/300KB).** Framebuffer in SRAM: correct and non-negotiable. Palette and DMA scratch: fine. Two additions recommended: an explicit **65KB SRAM tile slot** for the current GOP chunk. Right now GOP lives only in `pal_psram_gop_copy`, which means the per-frame, per-tile inner blit loop reads PSRAM. On ESP32-S3, cached octal PSRAM may sustain this at acceptable frame rates, but it is the single most likely performance cliff, and you have 220KB of SRAM headroom — spend 65KB on it (or at minimum make it a build-time switch and let the M2/M3 perf smoke decide). Second, budget the **main task stack explicitly** (24–32KB) once the real engine runs: `script.c` opcode 0x0004 recurses the interpreter for script calls, and battle/UI paths were written assuming desktop stacks. Add `-fstack-usage` analysis at build time and `uxTaskGetStackHighWaterMark` logging at scene/battle transitions on target.

**PSRAM (2.13MB/8MB).** The 1MB sprite pin is adequate (worst audited scene ~812KB deduplicated) but tight enough that a pathological scene plus player sprites could brush the ceiling — bump to 1.25MB; headroom is ample. The 256KB save-state buffer comfortably covers 189KB saves. I don't see an explicit `gpScreenBak` equivalent in the symbol list; the engine's fade/transition code assumes a full-screen backup surface distinct from menu staging, so add a named 64KB `pal_psram_screen_bak` rather than overloading `pal_psram_menu_background` — overloading will eventually violate a lifetime assumption during a fade-inside-menu sequence. Battle needs a scene-compose buffer; give it its own named 64KB PSRAM buffer for now and revisit an SRAM union only if profiling justifies it (unions of named statics fight your symbol-budget tooling; keep buffers boring).

**NOR at 10.45/11MB is your tightest budget** — 95% of the partition, and unlike Q1, the "demote to compressed" escape hatch is gone because runtime decompression is now banned. The only demotion direction is NOR→TF. Pre-plan it now: FIRE (1.91MB) is the designated eviction candidate, staged through the existing 64KB `pal_psram_effect` buffer with a TF read at spell-cast time. Wire the pack builder so archive→pack assignment is a manifest-driven policy, and add a CI gate that fails when NOR utilization exceeds a threshold (say 97%) so growth is caught at build time. Note the placement consequence you've already implicitly accepted: with decompression banned, MAP and FBP live decoded on TF, so scene transitions cost ~130KB of TF reads and battle entry costs a 64KB TF background read. Both are fine as one-shot sequential reads, but they interact with the next point.

**TF/SPI-bus risk.** TF shares the SPI bus with the LCD, including the MISO/D-C shared pin. That's workable for the current pattern (read at transition, then flush frames), but it forbids overlapping TF streaming with display flushes. The RNG cutscene is the one place this bites: frame decode/display and read-ahead must interleave on one bus with pin-mode switching between them. Size the 128KB read-ahead against *measured* TF throughput with the pin-switching overhead included, and treat "RNG playback without underflow on hardware" as an explicit M6 gate. This same constraint will shape audio later — flag it now in the docs so audio design doesn't assume concurrent TF streaming.

## 6. Keeping the contract enforceable as the real engine returns

Your existing three-layer check (source patterns, undefined symbols, relocations) is the right skeleton. Additions:

- **Relocation-scoped heap enforcement per object file.** The realistic target rule is "no heap in PAL-derived objects," since ESP-IDF itself allocates during init. Your relocation scan already approximates this; make the object-file allowlist explicit so a new engine file entering the link is automatically covered.
- **Named-symbol registry.** Every `pal_sram_`/`pal_psram_` symbol must appear in a checked-in registry with size and owner; `nm` output is diffed against it. This turns "someone added a 64KB static in a moment of need" from silent drift into a reviewed change, which matters more and more as original files gain static scratch.
- **PROT_READ NOR simulation** in every native contract CI run, not just ad hoc — it's your only automatic detector of the read-only-mutation class (§7).
- **Divergence budget check** from M0, permanently.
- **Golden-trace replay in CI** for at least the short routes (title, one town, one battle) on every commit; long routes nightly.
- **Stack ceiling check**: worst-path static stack estimate from `-fstack-usage` plus call-graph, failing above the budgeted task stack minus margin. Static analysis over-approximates around function pointers (the script interpreter's dispatch is a giant switch, so it's mostly analyzable), so pair it with the runtime watermark on target.

## 7. Hidden risks, ranked by expected pain

**Writes into "read-only" data — this will fire; find it in M0–M2, not on target.** Three known classes in SDLPAL: (a) `global.c` performs in-place load-time transformations on game data (endianness handling and DOS-version fixups) — running that code over a NOR const view is a fault on native and a *silent no-op* on memory-mapped flash, which is the worst failure mode; all such fixups must be baked by `pal_pack_build.py` and the runtime code path skipped, verified byte-exact against the desktop-loaded result. (b) The script interpreter advances event-object trigger/auto script addresses (opcodes 0x0002/0x0003 rewrite the event object's script entry fields) — safe, because the event-object table is already a mutable PSRAM copy, but it's a reminder that the *table split* between NOR templates and PSRAM copies must follow mutation reality, not tidiness. (c) There are code paths and historical SDLPAL variants that patch script entries directly in the script table (failsafe/one-shot patterns). Don't litigate this from memory — let the PROT_READ harness rule. If any script-table write exists, the cheap correct answer is to move the 340KB script table into a PSRAM copy (you have nearly 6MB free) rather than surgically proving each write benign.

**SDL surface semantics.** Engine code assumes surfaces with `pitch`, `SDL_FillRect`, and blit behavior — some of it *outside* `video.c`, in `ui.c`/`uigame.c`/`battle.c`. `pal_video_static.c` should present a minimal surface struct with `pixels`/`pitch`/`w`/`h` and shim implementations of the handful of SDL calls the engine files use directly, rather than editing every call site. Pitch must be honored, not assumed equal to width, or you'll re-fight blit bugs already solved upstream.

**Timing.** Fades, battle pacing, script waits, and animation all derive from real-time ticks. The virtual clock isn't just a determinism tool — it's also your target frame-pacing mechanism, since target frame times will differ from desktop. Get the seam right once in M1 and both problems are solved together.

**Sprite lifetime and ownership in `res.c`.** The original code frees and reloads sprite buffers on scene change and player-party change, and other code holds raw pointers across those events. When sprites become const NOR views or pin-cache slots, the *invalidation points* must match the original free points exactly, or you'll trade use-after-free (which crashes loudly on desktop) for stale-pin rendering (which fails silently). Make pin-cache invalidation an explicit call placed exactly where the original `free` calls were.

**PSRAM latency currently invisible.** Native SDL runs everything at DRAM speed. The candidates that will look different on target: per-tile GOP reads (mitigated by the SRAM tile slot), sprite blits from NOR through the flash cache (measure with a real scene, watch for cache contention with XIP code fetch), and full-frame PSRAM↔SRAM copies during fades/restores (bandwidth-fine but worth counting). Add a per-frame "PSRAM/NOR bytes touched" counter to the engine build so the native harness can at least report the *volume* even though it can't feel the latency.

**The C++ RIX player** stays out of the target link until audio returns; verify the contract check would catch an accidental `new` if it ever gets pulled in.

## 8. On your acceptance bar

Confirmed, with four tightenings. First, add determinism explicitly: point 4 should read "deterministic scripted routes *under record/replay with virtualized clock and seeded RNG* produce checkpoint outputs matching stock desktop SDLPAL," because without the determinism harness, "comparable" degrades to eyeballing. Second, add battle and RNG cutscene parity as named requirements — they're the two subsystems where drift is most likely and least visible in casual testing. Third, add the divergence budget as a standing gate, not a one-time review. Fourth, add one hardware item *before* the bar is fully cleared rather than after: the early target performance smoke of the real draw path (§3, M2–M3).
