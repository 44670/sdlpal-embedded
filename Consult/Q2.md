# Consultation Q2: CoreS3 SE Port Direction After Reverting Game-Logic Experiments

## Ask

Please review the current SDLPAL embedded port direction and recommend a practical plan for getting the full game running on M5Stack CoreS3 SE without changing game logic.

The expert reading this can assume zero prior knowledge of this project. The key question is not "can we render a scene?" anymore. We already have target-side resource-pack, LCD, touch, FatFS, and static-memory slices. The problem is how to wire those slices into the real SDLPAL engine while preserving the original game/script semantics.

Specific guidance requested:

1. What should the next architecture step be: continue replacing full-engine subsystems under compile-time contract flags, or build a separate target runtime that calls shared static resource APIs?
2. How should we avoid accidentally rewriting or approximating PAL script/game behavior?
3. What is the right native SDL2 verification strategy before flashing CoreS3 SE?
4. What checks should be added so "no heap, no runtime decompression, static buffers only" remains enforceable while the real game loop is restored?
5. Are the current SRAM/PSRAM/NOR/TF placements sane for this hardware, or should any buffers/resources move?

## Hard Requirements

- Target board is **M5Stack CoreS3 SE**, not CoreS3.
- Fast SRAM: 300KB total.
- PSRAM: 8MB total, much slower than SRAM.
- NOR flash: 16MB total, read-only at runtime, random accessible.
- TF card: effectively unlimited capacity, but slow.
- Original PAL data path for audits and pack builds:

```text
/mnt/hgfs/deb13/PAL
```

- No target runtime heap allocation:
  - no `malloc`
  - no `calloc`
  - no `realloc`
  - no `free`
  - no C++ `new` / `delete`
- No memory pool abstraction. Use normal named static variables/buffers.
- Use `uint8_t` arrays for SRAM/PSRAM buffers.
- Use `const uint8_t *` or typed `const` views for read-only NOR pack data.
- No runtime decompression. All YJ1/YJ2/VOC/text/font conversion must happen before building resource packs.
- TF resource-pack and save-file I/O should use ESP-IDF FatFS.
- Test with native SDL2 builds before target changes whenever possible.
- Verify resource usage from ELF/build artifacts with `size`, `objdump`, `nm`, map files, and pack checks.
- No OGG/OPUS/MP3/AVI support is needed for the current data set. The audited data has no loose `.ogg`, `.opus`, `.mp3`, `.wav`, `.mid`, or `.avi` files. Audio data is in PAL MKF containers: `MIDI.MKF`, `MUS.MKF`, and `VOC.MKF`.
- No audio on the CoreS3 SE target for now. The target app should not link `pal_audio_static.c` / `pal_sfx_cache.c` or reserve the SFX bank until hardware playback is in scope.

## Important Project Context

This repository is SDLPAL, an SDL-based engine for the classic Chinese RPG "Legend of Sword and Fairy" / PAL. The desktop engine is mostly C, with a C++ RIX music player. The original game data is proprietary and external to the repo.

The original desktop path uses:

- SDL surfaces/textures and SDL audio.
- `FILE *` filesystem access.
- direct heap allocation in many subsystems.
- runtime MKF reads and YJ decompression.
- game logic spread across `script.c`, `scene.c`, `res.c`, `global.c`, `uigame.c`, `battle.c`, `fight.c`, `rngplay.c`, `ending.c`, and related files.

Current target strategy from Q1:

- Build generated runtime-native resource packs on the host.
- Put hot read-only generated assets in NOR.
- Put large native assets in a TF-backed pack.
- Copy only current working-set chunks into named static SRAM/PSRAM buffers.
- Keep game data views read-only when possible.
- Keep mutable save/game state in named PSRAM buffers.
- Prove all of this first with native SDL2 and contract checks.

## Resource Pack Strategy

The host-side pack builder is:

```text
tools/pal_pack_build.py
```

It builds:

```text
/tmp/pal_nor_default.pak
/tmp/pal_tf_default.pak
/tmp/pal_pack_default_manifest.json
```

The pack builder is allowed to perform YJ1 decode, VOC conversion, text conversion, and other preprocessing because it runs on the host before deployment. The target runtime should only see native payloads.

Current default generated pack sizes from the latest `make -C esp32s3 check`:

- NOR pack: `10,446,724 / 11,534,336` bytes
- TF pack: `47,309,294` bytes

The custom target partition table reserves an 11MB read-only `pal_nor` partition inside 16MB flash. The current NOR pack fits, but not by a huge margin.

The target TF pack path is:

```text
0:/pal_tf.pak
```

Saves use short FatFS paths such as:

```text
0:/1.rpg
```

FatFS long filename heap support and dynamic FatFS buffers are disabled.

## Dataset Facts

The current PAL data set at `/mnt/hgfs/deb13/PAL` appears to be a DOS/YJ1 data set.

Major archive facts from the previous audit:

| File | Notes |
| --- | --- |
| `MAP.MKF` | 226 chunks, most YJ1-compressed; decoded map chunks are normally 64KB. Total decoded map tile data is about 14.6MB. |
| `GOP.MKF` | raw map tile sprites, about 11.5MB total; largest chunks about 65KB. |
| `MGO.MKF` | scene/player/event sprites; 636 YJ1 chunks; decoded total about 3.36MB. |
| `ABC.MKF` | enemy sprites; decoded total about 2.15MB. |
| `FIRE.MKF` | magic/effect sprites; decoded total about 1.91MB. |
| `FBP.MKF` | 72 full-screen backgrounds; each decoded frame is 64,000 bytes; decoded total about 4.6MB. |
| `F.MKF` | player battle/summon sprites; decoded total about 0.33MB. |
| `RNG.MKF` | cutscene animation streams; largest raw movie chunk about 1.27MB. |
| `VOC.MKF` | SFX source data; host pack builder converts these to PCM16 SFX chunks. |
| `SSS.MKF` | scripts, scenes, object table, event object table. |
| `DATA.MKF` | structured data and UI resources. |

Important conclusion: full pre-decompression into 16MB NOR is not feasible. Generated native assets must be split between NOR and TF.

Text/font facts:

- `WORD.DAT` + `M.MSG` decode cleanly as CP950.
- The text corpus uses 2,631 unique characters.
- Generated TEXT archive currently stores words/messages as UTF-16LE read-only spans in NOR.
- Generated FONT archive stores 2,600 unique 32-byte glyphs from `WOR16.ASC`/`WOR16.FON`.
- Missing glyphs are mostly handled by ASCII path plus a few CJK edge cases needing final fallback handling.

Save facts:

- Observed saves are under 189KB.
- A 256KB static PSRAM save-state buffer is enough for current save I/O experiments.

## Current Codebase State

There are two major implementation tracks:

1. Static resource/cache slices under `embedded/`.
2. A first ESP-IDF CoreS3 SE target app under `esp32s3/`.

Useful static slices already exist:

- `embedded/pal_pack.c`: no-heap pack reader, `const uint8_t` mapped reads, TF TOC copy/read-at API.
- `embedded/pal_scene_cache.c`: loads native MAP/GOP and scene MGO references/pinning using fixed buffers.
- `embedded/pal_battle_cache.c`: battle background/sprite/effect cache shapes.
- `embedded/pal_rng_cache.c`: predecoded RNG frame stream loading into fixed buffers.
- `embedded/pal_global_cache.c`: mutable global/default state copied to PSRAM, scripts/data mapped read-only.
- `embedded/pal_script_static.c`: read-only script entry view and bounded tracing only; **not a full interpreter**.
- `embedded/pal_text_cache.c`: generated UTF-16 text cache.
- `embedded/pal_font_cache.c`: generated glyph cache.
- `embedded/pal_save_cache.c`: save read/write through fixed PSRAM buffer.
- `embedded/pal_video_static.c`: indexed framebuffer, backup, scanline RGB565 conversion.
- `embedded/pal_ui_cache.c`, `pal_menu_static.c`, `pal_ending_static.c`, `pal_palette_static.c`, `pal_dialog_static.c`: static UI/menu/ending/palette/dialog asset/scratch shapes.
- `embedded/pal_noheap.c`: wrapper traps for heap calls in smoke tests.

The CoreS3 SE app currently does this:

- Initializes CoreS3 SE LCD/touch/TF using adapted board code.
- Maps the generated NOR pack from the `pal_nor` partition.
- Opens `0:/pal_tf.pak` through FatFS.
- Copies the TF pack TOC into `pal_psram_tf_toc`.
- Loads static TEXT/FONT/UI/menu/battle/RNG/music/ending/global/script views.
- Reads a startup save from `0:/1.rpg` through `0:/5.rpg` if present.
- Loads a scene using `PalScene_LoadPinnedSnapshotReadAt*()`.
- Draws a 320x200 indexed framebuffer centered on the 320x240 LCD with 20-pixel bars.
- Handles basic touch movement and previous/next scene selection.
- Saves only basic runtime position fields back into the loaded save buffer.

The current CoreS3 SE app is still a bring-up scaffold. It is not the full game loop.

## Important Recent Revert

An experimental path tried to advance the CoreS3 SE scaffold by adding target-side script operation handling directly inside `esp32s3/main/app_main.c`. That was the wrong direction because it started approximating game/script logic instead of preserving SDLPAL's original behavior.

Those game-logic changes were reverted with normal git revert commits. The revert range covered:

- scene save persistence experiments
- target-side auto/trigger/scene-enter script execution subsets
- added bounded script-op coverage gate
- dialog/shop/battle/RNG/FBP script previews
- inventory/party/palette/chase/teleport/touch-trigger handling
- screen shake/wave rendering tied to script state

Current HEAD after the reverts:

```text
f04eee4 Revert "Persist CoreS3 SE scene saves"
```

The key lesson: do not grow a parallel PAL interpreter in `esp32s3/main/app_main.c`. The target should either run the original engine logic with embedded-safe resource/video/input backends, or share exact upstream functions after replacing their allocation/resource dependencies.

## Native SDL2 Contract Track

There is also a Unix/native SDL2 contract profile:

```sh
make -C unix EMBEDDED_CONTRACT=1 contract-check
```

Its purpose is to make a reduced full-engine build that uses static resource APIs and generated packs while checking:

- no active project heap calls
- no C++ allocation operators
- no runtime decompressor symbols
- no active loose PAL resource filename usage except saves
- no large `PAL_LARGE` scratch buffers in active contract sources
- generated pack manifest/source hashes
- NOR pack budget
- symbol totals for named SRAM/PSRAM-style buffers

This profile is important because it can run under native SDL2, which is much easier to inspect than hardware.

However, it is still a reduced baseline. It is not yet proof that the complete original game loop runs correctly on target-style storage and buffers.

## The Core Design Problem

We need to get from a target scene scaffold to the real PAL game loop without changing game logic.

Bad direction:

- Add a simplified script interpreter to `esp32s3/main/app_main.c`.
- Add only the opcodes encountered by a bounded scan.
- Replace battle/menu/dialog/RNG behavior with short previews.
- Approximate movement, triggers, shops, or saves.

That can make demos pass but risks drifting from the game.

Preferred direction, likely:

- Keep original `script.c`, `scene.c`, `res.c`, `uigame.c`, `battle.c`, `fight.c`, etc. as the source of game behavior.
- Add embedded-safe compile-time paths under strict flags such as `PAL_NO_RUNTIME_HEAP` and `PAL_NO_RUNTIME_DECOMPRESS`.
- Replace resource acquisition, scratch buffers, video/audio/input, and filesystem glue while leaving game semantics in original functions.
- Use native SDL2 contract builds and scripted tests/golden frames to detect behavior drift.

The expert should confirm or correct this.

## Suggested Direction To Review

The current recommendation from the implementer side is:

1. Freeze the CoreS3 SE scaffold as a hardware/resource smoke app only.
2. Stop adding game/script behavior to `esp32s3/main/app_main.c`.
3. Put effort into the native SDL2 `EMBEDDED_CONTRACT=1` full-engine build.
4. Make that native build run the real game loop using generated packs and static buffers.
5. Add comparisons against the normal desktop build for script traces, save-state changes, and framebuffer CRCs.
6. Once native contract behavior is close enough, reuse the same full-engine/static-resource path on CoreS3 SE, replacing SDL presentation/input with CoreS3 SE LCD/touch/FatFS glue.

Please critique this plan, especially any places where it underestimates:

- stack/SRAM pressure
- PSRAM speed cost
- TF read latency
- original engine assumptions about mutable resources
- SDL wrapper behavior that will disappear on hardware
- risk from compile-time contract branches inside original source files

## Non-Goals

- Do not design a generic allocator or memory pool.
- Do not add runtime decompression to the target.
- Do not add OGG/OPUS/MP3/AVI playback for this data set.
- Do not continue a parallel simplified game interpreter in the CoreS3 SE app.
- Do not optimize for a fixed scene demo as the final result.
- Do not rely on the TF card for high-frequency random reads during rendering/audio callbacks.
