# Consultation Q2: Full-Game CoreS3 SE Port Strategy Without Rewriting PAL Logic

## Ask

Please review the current SDLPAL embedded-port direction and recommend the safest architecture for reaching the **full original game loop** on **M5Stack CoreS3 SE** without reimplementing or approximating PAL game logic.

This note is for an expert with **zero prior knowledge** of this codebase. It should be read as a continuation of `Consult/Q1.md`, but it is self-contained and restates the important background.

The key problem has changed since Q1:

- Q1 was mainly about memory placement, offline asset conversion, and feasibility under 300KB SRAM / 8MB PSRAM / 16MB NOR.
- Q2 is about **how to get from a hardware/resource bring-up scaffold to the real SDLPAL engine without semantic drift**.

The concern is not whether we can draw a scene. We already can. The concern is that an earlier attempt started adding target-side script/game behavior directly in the CoreS3 SE app, which is the wrong direction because it duplicates or simplifies real PAL logic.

Please answer these questions:

1. Should the next step continue the current compile-time `PAL_NO_RUNTIME_HEAP` / `PAL_NO_RUNTIME_DECOMPRESS` full-engine path, or should the project define a cleaner new resource/platform abstraction and move the original engine behind it?
2. How should the port preserve original behavior in `script.c`, `scene.c`, `res.c`, `battle.c`, `uigame.c`, `fight.c`, and related files while still enforcing fixed memory and offline-generated assets?
3. What verification strategy on native SDL2 would best prove that the embedded/static-buffer path still behaves like normal SDLPAL before flashing CoreS3 SE hardware?
4. What checks should be added so that "no malloc, no runtime decompression, static named buffers only" remains enforceable while the real game loop comes back?
5. Is the current SRAM/PSRAM/NOR/TF placement reasonable, or are there obvious misplacements that should change before further integration?

## Non-Negotiable Constraints

These are not open design questions.

- Target board is **M5Stack CoreS3 SE**, not CoreS3.
- Fast SRAM: **300KB total**.
- PSRAM: **8MB total**, much slower than SRAM.
- NOR flash: **16MB total**, read-only at runtime, random accessible.
- TF card: effectively unlimited capacity, but slow.
- Current PAL data set path:

```text
/mnt/hgfs/deb13/PAL
```

- Runtime allocation rules:
  - no `malloc`
  - no `calloc`
  - no `realloc`
  - no `free`
  - no C++ `new`
  - no C++ `delete`
- No memory-pool abstraction. Use normal named static variables and arrays.
- Runtime storage should be explicit:
  - `uint8_t` arrays for SRAM/PSRAM buffers
  - `const uint8_t *` or typed `const` views for read-only NOR pack data
- No runtime decompression. YJ1/YJ2/VOC/text/font conversion belongs only in host-side build tools.
- TF resource-pack and save-file I/O should use ESP-IDF FatFS.
- The native SDL build should stay usable as a verification harness.
- Resource usage should be checked from ELF/build artifacts with `size`, `objdump`, `nm`, linker maps, and pack checks.
- No OGG/OPUS/MP3/AVI support is needed for the current data set.
- No target audio for now. The CoreS3 SE target app should not link `pal_audio_static.c` / `pal_sfx_cache.c` or reserve the SFX bank until hardware playback is in scope.

This repository is SDLPAL, an SDL-based reimplementation of the classic Chinese RPG "Legend of Sword and Fairy" / PAL.

Important facts:

- The desktop engine is mostly C, with a C++ RIX music player.
- The original desktop path uses SDL surfaces/textures/audio, `FILE *`, heap allocation, runtime MKF reads, and runtime YJ decompression.

## What Q1 Already Established

Q1 already covered the main memory/asset feasibility result:

- Full pre-decompression into 16MB NOR is not feasible.
- The correct direction is host-side conversion into runtime-native packs.
- Hot read-only generated assets can live in NOR.
- Large generated native assets must live in TF-backed packs.
- Runtime should copy only current working-set resources into named static SRAM/PSRAM buffers.
- Runtime should map read-only assets as `const uint8_t *` where possible.
- The native SDL path should be used to verify the static-buffer design before target deployment.

The current accepted storage shape is:

- **NOR pack**: hot read-only generated assets.
- **TF pack**: large generated native assets.
- **PSRAM**: large mutable working sets, save state, scene staging, pinned sprites, RNG frames, FBP staging, menu scratch.
- **SRAM**: indexed framebuffer, tiny palette scratch, LCD DMA scratch, other hot small buffers.

## Why the Desktop Path Cannot Simply Be Reused As-Is

The need for contract/static-buffer work is not theoretical. Q1 already identified several current desktop-era memory problems:

- `fontglyph.h` keeps a mutable `unicode_font[65536][32]` table: about `2MB`.
- The same font path also carries additional width/offset tables.
- `resampler.c` has about `147KB` of mutable float LUTs.
- `global.c` heap-loads the main PAL global/script data set at roughly `532KB` on this corpus.
- Desktop save/load allocates roughly `184KB` to `189KB` per save operation for this corpus.
- Worst measured normal scene residency was about `909KB` before deduplication and before counting several other buffers.
- The same scene subset drops to about `143KB` after event-sprite deduplication, which is why sprite dedup/pinning matters.
- Several legacy paths use `PAL_LARGE` 64KB scratch buffers or allocate full-screen temporary surfaces.

So the embedded-port problem is not just "replace SDL". The desktop engine assumes resource shapes and temporary memory use that do not fit the CoreS3 SE rules without structural replacement underneath the original logic.

### CoreS3 SE Target App

The current target app in `esp32s3/main/app_main.c` is a bring-up scaffold. It currently:

- initializes LCD/touch/TF
- maps the NOR pack from the `pal_nor` partition
- opens `0:/pal_tf.pak`
- copies the TF TOC into `pal_psram_tf_toc`
- loads static TEXT/FONT/UI/menu/battle/RNG/music/ending/global/script views
- reads startup save headers and loads one save if present
- loads a scene through `PalScene_LoadPinnedSnapshotReadAt*()`
- draws a 320x200 indexed framebuffer centered on the 320x240 LCD
- handles simple touch-based movement and previous/next scene selection
- keeps scene draw metadata in normal static storage
- falls back to a synthetic background if TF is missing

It is **not** the original SDLPAL gameplay loop.

## Current Native SDL2 Contract Track

There is also a native SDL2 contract profile:

```sh
make -C unix EMBEDDED_CONTRACT=1 contract-check
```

Its role is extremely important. It is the only practical place to prove that the **real engine** can run with:

- no project heap usage
- no runtime decompression
- generated NOR/TF packs
- statically declared buffers
- reduced loose-file assumptions

The contract profile already does a lot:

- excludes desktop-only codec/player paths
- omits runtime decompressor code from the reduced profile
- wraps heap calls
- checks active source for forbidden patterns
- checks linked binary for forbidden symbols/calls
- verifies generated packs and manifest hashes
- budgets NOR size and named symbol totals

But it is still only a **reduced full-engine baseline**, not proof that the entire original game loop is correct on target-style storage.

## What Went Wrong Recently

An earlier attempt tried to make the CoreS3 SE target app "more complete" by adding target-side script and gameplay behavior directly into `esp32s3/main/app_main.c`.

That path added simplified or bounded behavior such as:

- save-state mutation from the scaffold
- scene-enter / auto / trigger script subsets
- bounded script-op coverage gating
- dialog/shop overlays in the scaffold
- FBP, RNG, and battle previews
- movement/chase/trigger handling tied to the scaffold
- screen wave/shake rendering tied to script state

That direction was wrong for one reason:

- it started building a **parallel PAL interpreter/runtime** instead of preserving the original engine's semantics

Those changes were reverted with normal `git revert` commits. The important meaning of the revert is architectural:

- the CoreS3 SE scaffold should not keep growing into its own simplified PAL runtime
- game logic should come from the original engine path, with storage/resource/platform layers adapted underneath it

The runtime behavior now corresponds to the reverted state rooted at:

```text
f04eee4 Revert "Persist CoreS3 SE scene saves"
```

Later doc-only commits do not change that runtime conclusion.

## The Actual Design Problem

The project now has enough evidence that fixed buffers, generated packs, and CoreS3 SE hardware access are viable.

The real question is how to restore the game safely.

Two broad directions are possible:

### Direction A: Keep the Original Engine Logic, Replace Subsystems Under It

This means:

- preserve original game logic in `script.c`, `scene.c`, `res.c`, `battle.c`, `fight.c`, `uigame.c`, and related files
- continue adding embedded-safe contract paths under compile-time flags
- replace resource acquisition, scratch buffers, save I/O, video pixel storage, and platform glue
- let original functions remain the source of truth for behavior

Benefits:

- least semantic drift
- easier to compare against standard desktop SDLPAL
- avoids inventing a second PAL interpreter

Risks:

- contract branches inside original files can become hard to reason about
- original code has many hidden assumptions about mutable buffers, surfaces, timing, and resource lifetimes
- if the resource/platform abstraction remains too ad hoc, maintenance cost will grow

### Direction B: Build a New Target Runtime on Shared Static Resource APIs

This means:

- keep static pack/cache/resource slices
- keep platform code in ESP-IDF
- gradually rebuild gameplay behavior in a new runtime that consumes the static slices

Benefits:

- clearer target-specific control
- no need to preserve desktop-era layering

Risks:

- very high semantic drift risk
- duplicated gameplay logic
- enormous testing burden
- likely endless opcode and edge-case chase in scripts, battle flow, UI flow, save flow, and event logic

The recent revert is strong evidence that Direction B is the wrong path for this project unless there is a very compelling reason the original engine cannot be preserved.

## Current Working Hypothesis

The current implementer-side hypothesis is:

1. Freeze `esp32s3/main/app_main.c` as a hardware/resource smoke app only.
2. Stop adding more gameplay or script behavior there.
3. Push the real effort into the native SDL2 contract full-engine path.
4. Make that contract path run more and more of the original SDLPAL loop using generated packs and static buffers.
5. Add strong comparisons against normal desktop SDLPAL.
6. Once the contract path is trustworthy, reuse that same engine/static-resource path on CoreS3 SE and keep the ESP-IDF side narrow: LCD, touch, FatFS, pack mapping, timing, and audio later.

Please critique this plan.

## Specific Background That Matters for the Expert Review

### 1. Static Resources Already Replace Many Desktop Shapes

The repo already has embedded/static replacements or proofs for:

- pack mapping and TF TOC copy
- scene MAP/GOP loading
- scene sprite deduplication and pinning
- read-only script entry access
- text cache
- font cache
- save-state buffer
- indexed framebuffer and restore buffers
- menu background/image/box scratch
- ending FBP staging
- RNG frame staging
- battle background/effect staging
- palette scratch

So this is not a blank-slate port.

### 2. The Remaining Hard Part Is Original Semantics

The difficult part is not "can we read the pack?".

The difficult part is:

- original script flow
- scene enter/teleport/auto/trigger behavior
- menu transitions
- battle flow
- RNG playback behavior
- save/load integration
- exact state mutation semantics

Those are why building a simplified target runtime is dangerous.

### 3. Memory Pressure Is Real but Not Yet the Main Risk

Current target named SRAM usage is only about `78KB / 300KB`, which is comfortable.

Current target named PSRAM usage is about `2.13MB / 8MB`, which is also comfortable.

That does **not** mean the full game is done. It only means the current static resource shapes are plausible.

The main risk now is semantic correctness, not raw byte budget.

### 4. The Native Contract Path Is the Real Safety Net

If the team cannot prove behavior equivalence on native SDL2, it will be much harder to debug on hardware.

The expert should assume that **native contract verification is mandatory** before any serious target-side gameplay integration.

## Suggested Acceptance Bar Before More Target-Side Gameplay Work

The current suggested bar is:

1. Native SDL2 contract build runs the original game loop, not a scene scaffold.
2. Generated NOR/TF packs are the only runtime game-asset source in that profile, except saves.
3. Contract profile stays at zero forbidden heap/decompress/project-call hits.
4. Deterministic scripted routes produce checkpoint outputs comparable to normal desktop SDLPAL.
5. Save-load round trips preserve expected state.
6. Only after that should CoreS3 SE hardware glue be asked to host more of the real game.

Please confirm or reject this bar and recommend a better one if needed.
